# Kotlin Rules

Framework-specific rules layered on top of [`.ai/constitution.md`](../../.ai/constitution.md). Same rule format and tags — see the constitution for field/tag definitions. Reference: [Kotlin docs](https://kotlinlang.org/docs/home.html).

- **ID format:** `<CATEGORY>-NNN` (e.g. `SEC-001`) — unique within this file, no framework prefix needed since this file is already the Kotlin-scoped table.
- **Detected by:** `*.kt` source files present, or a Gradle build file (`build.gradle`/`build.gradle.kts`) referencing the `kotlin("jvm")` or `org.jetbrains.kotlin` plugin
- General-purpose Kotlin language rules go here; rules specific to a Kotlin framework or ecosystem (e.g. Fabric mod development) go in that framework's own file — see [`.frameworks/fabric/rules.md`](../fabric/rules.md) for Fabric+Kotlin intersection rules like `fabric-language-kotlin` entrypoints.

## Rules

| ID | Title | Description | Mutability | Enforcement |
|---|---|---|---|---|
| `DEV-001` | `!!` Bypasses Null Safety Entirely — Prefer a Safe Call, Elvis, or an Explicit Check | Most Kotlin NPEs come from only a few sources: an explicit `throw NullPointerException()`, `!!` on a null value, uninitialized-`this` leaking during construction, or Java interop. Java-returned types are "platform types" the compiler can't verify as nullable or not, so nulls crossing that boundary (e.g. a Java method putting `null` into a `MutableList<String>`) are a common uncaught source. Reserve `!!` for cases truly guaranteed non-null; anywhere else, a safe call (`?.`), Elvis (`?:`), or an explicit `if`/`require` check keeps the failure mode a controlled one instead of a raw NPE with no context. | `mutable` | `warning` |
| `DEV-002` | A Safe-Call Chain on the Left Side of an Assignment Short-Circuits the Right Side Too | `person?.department?.head = manager()` never calls `manager()` if `person` or `person.department` is null — the entire right-hand expression is skipped, not just the assignment. Putting a side effect (logging, a mutation, an API call) on the right side of a safe-call assignment means that side effect silently doesn't happen on the null path, which is easy to miss since there's no exception or warning. | `immutable` | `warning` |
| `DEV-003` | Structural Equality Has Sharp Edges: Arrays Need `contentEquals()`, and Float/Double `NaN`/`-0.0` Behavior Depends on Static Type | `==` compiles to a null-safe `equals()` call, but `Array` doesn't override `equals()` — `arrayOf(1,2,3) == arrayOf(1,2,3)` is `false` (referential); use `contentEquals()` for structural array comparison. Separately, `Float`/`Double` follow IEEE 754 when statically typed as such (`NaN != NaN`, `-0.0 == 0.0`), but the same values boxed as `Any` or compared via generics use structural equality instead (`NaN == NaN`, `-0.0 != 0.0`) — the same two numbers can compare differently depending on how they're typed at the comparison site. | `immutable` | `warning` |
| `DEV-004` | A Data Class's `equals()`/`hashCode()`/`toString()`/`copy()` Only See Primary-Constructor Properties, and `copy()` Is Shallow | A property declared in the class body (not the primary constructor) is invisible to the generated `equals()`, `hashCode()`, `toString()`, and `copy()` — two instances that differ only in a body property compare equal. Separately, `copy()` performs a shallow copy: a `MutableList` or other mutable reference held by the class is shared between the original and the copy, so mutating it through one instance is visible through the other. | `immutable` | `warning` |
| `DEV-005` | Sealed Class Subclassing Is Restricted, and Constructors Must Be `protected`/`private` | A sealed class's *direct* subclasses must live in the same package and module as the sealed declaration (indirect subclasses of an `open` direct subclass have no such restriction), and its constructors can only be `protected` or `private` — a `public`/`internal` constructor is a compile error. This is what lets a `when` over the sealed type skip an `else` branch and still be exhaustive; declaring a subclass outside the sealed hierarchy's package, or trying to give it a public constructor, breaks that closed-set guarantee. | `immutable` | `warning` |
| `DEV-006` | `object` Declarations Initialize Lazily on First Access; Companion Objects Initialize at Class Load — Don't Assume the Same Timing | A top-level or nested `object` declaration runs its `init` block the first time it's referenced (thread-safely, via JVM class-init semantics), while a `companion object` initializes when its enclosing class is loaded — code relying on singleton side effects (e.g. a static registry populated by an `init` block) can run at a surprisingly different time than expected if it assumes the two are interchangeable. Separately, always compare `data object` instances with `==`, not `===`: reflection (or deserialization) can produce a second instance that's structurally but not referentially equal to the canonical singleton. | `immutable` | `info` |
| `DEV-007` | `by lazy { }` Thread-Safety Mode and `observable()`/`vetoable()` Timing Are Easy to Get Backwards | `lazy { }` defaults to `SYNCHRONIZED` (computed once, visible to all threads); `LazyThreadSafetyMode.NONE` drops all thread-safety and must only be used when init and access are guaranteed to happen on the same thread, and `PUBLICATION` allows concurrent computation but discards all but the first result. Separately, `Delegates.observable()`'s handler runs *after* the new value is already assigned (it can't reject the change), while `Delegates.vetoable()`'s handler runs *before* assignment and must return a `Boolean` to allow (`true`) or reject (`false`) it — using `observable()` where rejection logic was intended silently lets every assignment through. | `mutable` | `warning` |
| `DEV-008` | `apply`/`also` Return the Receiver; `let`/`run`/`with` Return the Lambda's Result — Picking the Wrong One Silently Changes What You Get Back | `Person("John").run { age = 30 }` evaluates to `Unit` (the result of the assignment), not the `Person` — `apply` is the one that returns the configured receiver. Since both forms compile fine, this class of mistake surfaces as a wrong-typed or unexpectedly-`Unit` value downstream rather than a build error at the call site itself. | `mutable` | `warning` |
| `DEV-009` | Smart Casts Don't Apply to `var` Properties, Open/Custom-Getter Properties, or a `var` Local Captured by a Modifying Lambda | The compiler only smart-casts a value after a type check if it can prove the value can't change before it's used. A `var` class property is never smart-cast (other code could mutate it between the check and use); an `open` property or one with a custom getter isn't either, since a subclass override could return something else; and a local `var` is only smart-cast if no lambda that captures it also reassigns it. Each of these fails as a compile error at the use site, not silently — but the fix (copy to a local `val` first) is easy to miss under the assumption "I already checked the type." | `immutable` | `info` |
| `DEV-010` | `async { }` Swallows Its Exception Until `await()` Is Called — `launch { }` Propagates Immediately | An exception thrown inside `async { }` is captured on the resulting `Deferred` and stays silent — nothing is logged or thrown — until something calls `.await()` on it. Fire-and-forget code that starts an `async` and never awaits it (or awaits it much later, conditionally) can lose an exception's ever surfacing at all. `launch { }`, by contrast, propagates its exception immediately, uncaught-handler style. | `immutable` | `warning` |
| `DEV-011` | Coroutine Cancellation Is Cooperative — Tight Loops and JVM Blocking Calls Ignore It Unless You Check For It | A coroutine only reacts to cancellation at a suspension point or an explicit check; a CPU-bound loop with no `delay()`/`yield()` inside it runs to completion regardless of `cancel()` unless it checks `isActive`/`ensureActive()` itself, and a JVM blocking call like `Thread.sleep()` ignores coroutine cancellation entirely unless wrapped in `runInterruptible { }`. Separately, if code catches `CancellationException` for cleanup purposes, it must rethrow it — swallowing it silently breaks cancellation propagation up through the rest of the coroutine hierarchy, leaving parent/sibling coroutines running when they were meant to stop. | `immutable` | `warning` |
| `DEV-012` | `CoroutineExceptionHandler` Only Takes Effect on a Root Coroutine — Installing It on a Child Is Silently Ignored | A `CoroutineExceptionHandler` passed to a non-root `launch` (one with a parent job) never fires; the exception propagates to the parent instead, bypassing the handler entirely with no warning that it was ineffective. It only has an effect on a coroutine with no parent (e.g. one started directly in a top-level scope) or inside `supervisorScope`, where child failures don't automatically propagate up. | `immutable` | `warning` |
| `DEV-013` | A Plain `Job`'s Child Failure Cancels Its Siblings and Parent — Use `SupervisorJob`/`supervisorScope` for Independent Children | Under a regular `Job`, one child throwing an uncaught exception cancels the entire coroutine hierarchy above and beside it — siblings still mid-flight are torn down too. `SupervisorJob` (or `supervisorScope` for a scoped block) isolates each child's failure so siblings keep running; reach for it whenever child coroutines represent independent units of work (e.g. per-request handlers) rather than an all-or-nothing computation. | `mutable` | `warning` |
| `DEV-014` | Passing `Job()` as a Child Coroutine's Context Detaches It From Structured Concurrency | `launch(Job())` replaces the inherited parent job with a brand-new, unrelated one — the new coroutine no longer gets cancelled when its nominal parent is cancelled, and the parent no longer waits for it to finish. This defeats the whole point of structured concurrency (bounded lifetime, guaranteed cleanup) and is easy to reach for by accident when trying to "isolate" a coroutine, when `SupervisorJob`/`supervisorScope` is very likely what was actually wanted instead. | `mutable` | `warning` |
| `DEV-015` | `@Volatile` Makes Reads and Writes Atomic, Not Compound Operations Like `counter++` | `@Volatile` guarantees any thread sees the latest written value, but `counter++` is a read-modify-write sequence — two threads can both read the same value before either writes back, losing an increment. Under concurrent access, use `AtomicInteger`/`AtomicLong`, a `Mutex` (which suspends rather than blocking the thread, unlike `synchronized`), or coarse-grained single-thread confinement of the whole mutation, not `@Volatile` alone. | `immutable` | `warning` |
| `DEV-016` | Extension Functions Resolve Statically by Declared Type — There's No Virtual Dispatch, and a Member Function Always Wins | Which extension function gets called is decided at compile time from the variable's *declared* type, not its runtime type — passing a `Rectangle` to a function parameter typed `Shape` and calling an extension will run `Shape`'s extension even if `Rectangle` has its own. If a class has a member function with a matching signature, that member always wins over any extension with the same name, silently shadowing it (a differently-signatured extension can still coexist as an overload). | `immutable` | `info` |
| `DEV-017` | A Default Parameter Value Is Only Evaluated When the Argument Is Omitted, and Can Only Reference Earlier Parameters | Default-value expressions (including ones with side effects, like a `println` or a function call) run exactly when the caller doesn't supply that argument — passing the argument explicitly, even as the same value, skips evaluating the default expression entirely. A default value may reference other parameters, but only ones declared before it in the parameter list; and a parameter with a default can't precede a parameter without one unless callers use named arguments (a trailing lambda parameter is the one exception). | `immutable` | `info` |
| `DEV-018` | A Read-Only Collection Type (`List`/`Set`/`Map`) Is a View, Not a Guarantee of Immutability | Assigning a `MutableList` to a `val` typed `List` only removes *that reference's* ability to mutate the collection — if the same underlying mutable collection is still held (and mutated) elsewhere, the read-only view reflects those changes. Don't treat a `List`-typed parameter or property as safe from concurrent or external modification just because its declared type has no mutating methods; if true immutability is required, copy it (e.g. `toList()`) at the boundary. | `immutable` | `warning` |
| `DEV-019` | Mutable Collection Types Are Invariant — `MutableList<Sub>` Is Not a `MutableList<Super>` Even When `Sub` Extends `Super` | Unlike the read-only collection interfaces (which are covariant — a `List<Rectangle>` can be used as a `List<Shape>`), `MutableList<Rectangle>` cannot be assigned where `MutableList<Shape>` is expected. This isn't a compiler oversight — allowing it would let code add an unrelated `Shape` subtype (e.g. `Circle`) into a list that's actually backed by `Rectangle` storage. Reach for a read-only supertype view at the boundary instead of trying to force the mutable type to vary. | `immutable` | `info` |
| `DEV-020` | Destructuring Declarations Bind by Position via `componentN()`, Not by Variable Name | `val (a, b) = someDataClassInstance` calls `component1()`/`component2()` in order — the names `a`/`b` are irrelevant to what value ends up where. Reordering a data class's primary-constructor properties silently breaks or mis-assigns every existing destructuring call site for it, with no compiler error, since the call sites still type-check correctly against the new order. | `immutable` | `warning` |
| `DEV-021` | `lateinit` Throws `UninitializedPropertyAccessException`, Not `NullPointerException`, and Only Applies to Non-Primitive `var` Properties Outside the Primary Constructor | `lateinit` can't be used on `val`, on primitive types (`Int`, `Boolean`, etc.), on nullable types, or on a primary-constructor parameter — and code that expects a plain NPE from an uninitialized access (e.g. a broad `catch (e: NullPointerException)`) won't catch the actual exception type it throws. Check `this::property.isInitialized` before access when initialization order isn't guaranteed, rather than relying on catching the access exception after the fact. | `immutable` | `warning` |
