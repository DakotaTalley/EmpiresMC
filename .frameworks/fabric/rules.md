# Fabric (Minecraft Modding) Rules

Framework-specific rules layered on top of [`.ai/constitution.md`](../../.ai/constitution.md). Same rule format and tags — see the constitution for field/tag definitions.

- **ID format:** `<CATEGORY>-NNN` (e.g. `SEC-001`) — unique within this file, no framework prefix needed since this file is already the Fabric-scoped table.
- **Detected by:** `fabric.mod.json` present, or a Gradle build file (`build.gradle`/`build.gradle.kts`) referencing the `fabric-loom` plugin

## Rules

| ID | Title | Description | Mutability | Enforcement |
|---|---|---|---|---|
| `DEV-001` | `fabric.mod.json` Needs `schemaVersion: 1` First, a Conformant `id`, and Fully-Qualified Entrypoint Classes | Fabric Loader requires `schemaVersion` (must be `1`, placed first in the file), `id` (2–64 characters, starting with a letter, ASCII letters/digits/underscores/hyphens only), and `version` to recognize the mod at all. Entrypoints (`main`, `client`, `server`) are declared as arrays of fully-qualified class names (optionally `Class::method`); `main` implements `ModInitializer`, `client` implements `ClientModInitializer` and only runs on the physical client, `server` implements `DedicatedServerModInitializer` and only runs on the physical server. A typo'd entrypoint class name fails to load with no crash log pointing at the cause. | `immutable` | `warning` |
| `DEV-002` | The `environment` Field Restricts Where a Mod or Mixin Config Loads — Silently, Not With a Crash | `environment` (root level, and per-mixin-config in the `mixins` array) accepts `"*"` (default, all environments), `"client"` (physical client only, blocked on dedicated servers), or `"server"` (physical server only, blocked on clients and singleplayer). Setting the wrong value doesn't crash or log an error — the mod, or that mixin config, simply never loads on the excluded environment, surfacing later as "this feature doesn't work on server/client" with no obvious cause. | `immutable` | `warning` |
| `DEV-003` | Mixin Local Variable Table Indexing: `long`/`double` Locals Consume Two LVT Slots | When targeting a local variable by LVT index in a mixin (`@ModifyVariable`, `@LocalCapture`, etc.), each `long` or `double` local occupies two consecutive indexes, not one — miscounting past a wide local shifts every subsequent index off by one and silently targets the wrong variable. Static methods also have no implicit `this` at index 0, so the first parameter starts at index 0 there, unlike instance methods where it starts at index 1. | `immutable` | `warning` |
| `DEV-004` | Access-Widening a Private Final Field to Both `accessible` and `mutable` Requires Two Separate Entries | The access-widener file has no combined directive for "public and non-final" on a field — making a `private final` field both accessible and mutable requires one `accessible` entry and one separate `mutable` entry for the same field, not a single line. Access widening only works on Vanilla classes (not other mods' classes), and class-level entries must use internal names (`/`-separated, e.g. `net/minecraft/foo/Bar`) rather than dotted names — using a dotted name silently fails to match. | `immutable` | `warning` |
| `DEV-005` | A Registry Class's Fields Only Register Once Something Statically Initializes That Class | Registering items/blocks/etc. as `static final` fields on a holder class doesn't run that code until the JVM statically initializes the class — which only happens on first access. Referencing the class from elsewhere at the wrong time (or never) means the fields sit unregistered with no error, e.g. items that exist in code but never appear in creative tabs or the registry. The standard fix is a dummy `initialize()` method on the holder class, explicitly called once from the mod's entrypoint, so initialization timing is deterministic instead of relying on incidental first-touch. | `mutable` | `warning` |
| `DEV-006` | A Custom Fabric API Event Does Nothing Until a Mixin Injects the Call to Fire It | Declaring a callback interface plus an `Event` field built with `EventFactory.createArrayBacked()` only creates the event object — it does not make the event fire. The event's invoker must be called from a `@Inject` mixin placed at the precise point in vanilla (or another mod's) code where the event is meant to occur; forgetting this step leaves listeners registered but never invoked, with no error indicating why. | `mutable` | `warning` |
| `SEC-001` | Validate Every Packet Server-Side — the Logical Server Runs Even in Singleplayer, so Client State Is Never Trustworthy | A clientbound/serverbound payload is only a proposal from an untrusted process; a modified or malicious client can send arbitrary payload contents. Server-side handlers must independently verify entity existence, distance/range, and permissions before applying any game-state change described by the packet — don't apply it just because the packet arrived. This applies even in singleplayer, since the logical server still runs locally and still processes packets from the logical client the same way it would from a network client. | `immutable` | `stop` |
| `DEV-007` | Loom's `enableTransitiveAccessWideners` Defaults to `false` — a Dependency's Access Widening Isn't Inherited Unless You Turn It On | A mod dependency can ship its own access-widener file to open up vanilla members it needs, but Loom does not apply those transitively to your project unless `loom.enableTransitiveAccessWideners = true` is set. Left at the default, code that relies on a dependency's access widening compiles and runs fine in that dependency's own project but throws an `IllegalAccessError` at runtime in yours, with nothing in the build output pointing at the missing flag. | `mutable` | `warning` |
| `DEV-008` | `splitEnvironmentSourceSets()` Needs Both Source Sets Explicitly Added to the Mod DSL | Enabling Loom's client/common source-set split (`loom.splitEnvironmentSourceSets()`, requires MC 1.18+/Loader 0.14+/Loom 1.0+) only creates the separate `client` source set — it doesn't wire it into the mod on its own. Both `main` and `client` must be added via `loom.mods { modName { sourceSet(...) } }`, or client-only code fails to compile or bundle even though the source set exists on disk. | `mutable` | `warning` |
| `DEV-009` | Unit Tests That Touch Registry-Backed Classes Need an Explicit Bootstrap Call | Instantiating or reading anything backed by Minecraft's registries (e.g. building an `ItemStack`) in a JUnit test throws `IllegalArgumentException: Not bootstrapped` unless the registries have been initialized first via `SharedConstants.tryDetectVersion(); Bootstrap.bootStrap();`. Standard JUnit also can't run mixin-modified classes at all — the Fabric Loader JUnit dependency and `useJUnitPlatform()` are required, not just a plain JUnit setup. | `mutable` | `warning` |
| `DEV-010` | Recipes Are Server-Side Data — the Client Doesn't Know What Recipes Exist Unless You Synchronize Them | Recipe matching (`serverLevel.recipeAccess().getRecipeFor()`) only works on the logical server; the client has no local recipe registry to query by default. Code that needs recipe data client-side (a custom UI, a JEI-style plugin) must explicitly call recipe synchronization in the initializer, or it will silently find nothing rather than erroring. | `immutable` | `warning` |
| `DEV-011` | Debug-Level Log Messages Are Hidden by Default in the Dev Environment | `logger.debug(...)` calls produce no visible output in the run console until a `log4j-dev.xml` file is created, wired in via `loom.log4jConfigs.from("log4j-dev.xml")`, and configured with the mod's logger name at `debug` level — after which IDE run configurations typically need regenerating to pick it up. Reserve `debug()` for development-only noise and `info()`/`warn()`/`error()` for anything a modpack dev or end user should see in a normal log. | `mutable` | `info` |
| `DEV-012` | Key Mappings Are Client-Only, and Default Keycodes Assume a US Keyboard Layout | Key mappings exist only on the client — register and handle them exclusively from the client entrypoint; there is no server-side equivalent. GLFW key constants like `GLFW_KEY_J` name the physical key position on a US QWERTY layout, so on an AZERTY layout the key labeled 'A' actually sends `GLFW_KEY_Q` — don't assume a keycode constant matches the printed letter for all users. | `immutable` | `warning` |
| `DEV-013` | A Missing Translation Key Falls Back to Displaying the Raw Key, Not an Error | If a `Component.translatable` key has no matching entry in the active language file, Minecraft renders the literal key string in place of the text instead of throwing or logging — a missing or misspelled translation key is easy to miss during testing because nothing looks broken, just unpolished. | `immutable` | `info` |
| `DEV-014` | GameTest Environments Auto-Generate One Extra Passing Test Per Environment | Vanilla Minecraft's GameTest framework auto-generates one lightweight `net.minecraft.gametest.framework.GeneratedTest` per registered `TestEnvironmentDefinition` (e.g. `minecraft:default`, the default used by `@GameTest` unless `environment()` is overridden) to validate the environment setup itself, independent of any mod's declared tests. A `runGameTest` summary reporting `N+1` tests when only `N` were authored is expected framework behavior, not a bug, a duplicate registration, or a phantom failure to chase down. | `mutable` | `info` |
| `DEV-015` | A Mock/Embedded GameTest Player Is Permanently Invulnerable to `hurtServer()` — Call `die()` Directly to Test Death Logic | `ServerPlayer.isInvulnerableTo()` falls back to `true` whenever `connection.hasClientLoaded()` is `false`, which is always the case for a `GameTestHelper.makeMockServerPlayerInLevel()`-style mock/embedded connection (no real client ever sends the load acknowledgment) — so `hurtServer(level, source, amount)` silently returns `false` and leaves health unchanged for any damage source, even one tagged to bypass invulnerability (e.g. `/kill`'s `genericKill`), with no exception or log pointing at the cause. Call `entity.die(damageSource)` directly instead when a gametest needs to exercise real death-handling logic (loot drops, death events, inventory-drop behavior) on a mock player — `die()` only guards on `isRemoved()`/`dead`, not invulnerability, so it reliably runs the full death sequence. | `mutable` | `warning` |
