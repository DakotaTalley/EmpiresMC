# Phase 5 — Protection enforcement

Part of the [EmpiresMC 1.0 release plan](../1.0-release.md). Previous: [Phase 4](phase-4-claiming-and-unclaiming.md). Next: [Phase 6 — Claim visualization](phase-6-claim-visualization.md).

## Goal

The core rule of the mod is enforced: outside their claims the player cannot change the world — no breaking, no placing, no block-modifying item use — while ordinary interaction (doors, chests, looting structures) still works.

## Design decisions

- **The restriction model is inverted from classic claim mods.** Claims don't protect land *from others*; they define the only places the *player* may alter. Consequences that shape this phase:
  - Non-block gameplay stays free everywhere: movement, combat, item pickup, trading, sleeping.
  - "Pure" interactions (open door/chest, press button, use crafting table, loot generated structures) are **allowed** in the wild — exploration and looting are the intended counterweight to restricted mining. A strict-mode config toggle can come later; it is not MVP.
  - "Modifying" interactions (bucket place/drain, flint & steel, hoe till, shovel path, axe strip, bone meal) are **denied** in the wild — each is a block change wearing an interaction costume.
- **Explosion policy: left as vanilla, by decision.** Explosions behave identically in claims and the wild — no block-damage filtering. No Fabric API event exists for this, and the only interception points (filtering the explosion's block-damage list, or restricting pickup of the resulting drops) both require a mixin; rather than add mixin infrastructure for it, the call is to accept vanilla explosion behavior for 1.0. Rationale: world-destructive explosions read as consistent with vanilla Minecraft, and TNT/creeper mining the wild takes real setup and skill (positioning explosives, luring creepers) — a meaningfully higher bar than passive strip-mining. This reopens exploit-register item #3 in the [Phase 10 exploit register](phase-10-exploit-hardening-and-balance.md) as accepted/monitored rather than closed; revisit if the balance playthrough shows it's exploited more heavily than expected.
- **Creative mode bypasses all restrictions** (standard modding convention, and it keeps dev/testing fast). Survival/adventure enforce.
- **Denial feedback must not spam:** action-bar message + soft sound, throttled per player (~1/second), since holding left-click fires break attempts every tick.
- Implementation surfaces (confirmed against the pinned Fabric API version by decompiling the actual jars):
  - Break: `PlayerBlockBreakEvents.BEFORE` (authoritative cancel) + `AttackBlockCallback` (early client+server deny so blocks don't even crack).
  - Place: no mixin needed — `ItemEvents.USE_ON` wraps `Item.useOn(UseOnContext)`, the call `ServerPlayerGameMode.useItemOn` makes only *after* the clicked block's own reaction (door/chest/button/etc.) has already declined to consume the interaction, so denying here never preempts a pure interaction. (An earlier pass used `UseBlockCallback`, which fires at the *head* of `useItemOn` before the block gets a say — manual playtesting caught that this wrongly denied opening a door/chest whenever the player happened to be holding a deny-list or block item outside their claim; switching to `ItemEvents.USE_ON` fixed it. Root-caused by decompiling `ServerPlayerGameMode.useItemOn`'s actual call order.) Denial checks the *placement* position's chunk (built via a real `BlockPlaceContext`, not the clicked block's) — placing across a chunk border must check where the block lands, including a multi-block placement's companion half (beds; doors can't cross a chunk border, their second half is a pure vertical offset).
  - Modifying interactions: the same `ItemEvents.USE_ON` hook, filtered on a deny-list of modifying item classes (flint & steel, hoe, shovel, axe, bone meal) — except buckets, which override `Item.use(...)` instead of `Item.useOn(...)` and so never reach this hook at all; gated separately via `UseItemCallback` (which wraps `Item.use(...)`), doing its own raycast since that event carries no hit result.
  - Denial must **correct the client's prediction**, not just refuse the action. The client runs the same `ItemStack.useOn`/`use` it just packeted to the server (restoring the stack only in creative), so a server-side refusal leaves the client showing a consumed item — and because the server's stack never changed, the container menu has no diff to broadcast and never fixes it. Every denied *use* therefore resyncs the inventory; break denial doesn't need it (block mispredictions are covered by the prediction-sequence ack).
  - Denial feedback sounds must be sent **as a packet to the player**, never via `player.playSound(...)`, which on the server excludes that very player (it becomes the exclusion argument of `PlayerList.broadcast`). `util/PlayerSounds.playTo` is the one correct seam; anything else in this codebase playing a personal cue should route through it.
  - Central decision logic is split into three independently gate-able predicates — `canBreak`/`canPlace`/`canInteract` — rather than one shared check, so a future Phase 7 config can enable/disable break, placement, and modifying-item-use enforcement independently instead of all-or-nothing.

## Steps

- [x] Central `ProtectionService.canBreak`/`canPlace`/`canInteract(player, world, pos): ProtectionResult` (+ deny reason: wild vs. owned by someone else) so every hook shares one decision path per action kind — rules live in one place, hooks stay dumb, and each action kind is independently gate-able for Phase 7.
- [x] Wire break denial (both events), with the crack-prevention path verified.
- [x] Wire place denial via the placement-position chunk check, including multi-block placements (beds: check both halves; doors need no equivalent — their second half is a pure vertical offset and can't cross a chunk border).
- [x] Wire modifying-interaction denial: buckets (place and pickup), flint & steel, bone meal, hoe/shovel/axe right-click transforms.
- [x] Throttled action-bar denial feedback with translatable messages, distinguishing wild from owned-by-someone-else.
- [x] Creative bypass, applied identically across `canBreak`/`canPlace`/`canInteract` (single seam per predicate for the Phase 7 config toggles).
- [x] Gametests: break denied in wild / on someone else's claim / allowed in own claim; place denied in wild / allowed in claim; cross-border placement denied; bucket denied in wild; bone meal denied in wild; chest/door interaction *allowed* in wild; creative bypass works.

**Delivered:** new `com.dakotatalley.empiresmc.protection` package — `ProtectionResult` (sealed `Allowed`/`DeniedWild`/`DeniedOwnedByOther`, mirroring `ClaimResult`), `ProtectionService` (the three predicates above, stateless), `ProtectionFeedback` (throttled action-bar + sound denial), `ProtectionHooks` (registers `PlayerBlockBreakEvents.BEFORE`, `AttackBlockCallback`, `ItemEvents.USE_ON`, and `UseItemCallback` — no mixins, per the design decision above). Wired into `EmpiresMC.onInitialize()`; two new lang keys (`empiresmc.protection.denied_wild`/`denied_owned`). Plus `com.dakotatalley.empiresmc.util.PlayerSounds`, a shared seam for personal sound cues added while fixing the silent-feedback bug below (also adopted by Phase 4's `ScepterItem`). 14 new gametests added to `EmpiresMCGameTest.kt` covering every bullet above plus direct `ProtectionService` assertions for the wild-vs-owned-by-other distinction. `./gradlew clean build` green: full JUnit suite + all 32 gametests passing.

**Manual playtest findings (first `runClient` pass) and fixes:**
- Water bucket use in the wild showed the denial message but the bucket still placed/drained water. Root cause: `BucketItem` overrides the generic `Item.use(Level, Player, InteractionHand)`, not `Item.useOn(UseOnContext)`, so it never reached the original `UseBlockCallback` hook's placement/deny-list branch in any way that actually stopped it — that hook's denial only ever short-circuited a call that was already a vanilla no-op for buckets. Fixed by adding a dedicated `UseItemCallback` registration (wraps `Item.use(...)`) that replicates `BucketItem`'s own internal raycast to find what it's about to affect.
- Opening a door outside the claim was incorrectly denied whenever the player happened to be holding a placeable or modifying item (having just placed/tested one). Root cause: `UseBlockCallback` fires at the *head* of `ServerPlayerGameMode.useItemOn`, before the clicked block's own reaction (door toggle, chest menu, etc.) gets a chance to consume the interaction — so our hook was preempting pure interactions whenever the held item happened to match the deny-list or be a `BlockItem`, regardless of what was actually being clicked. Fixed by switching placement + modifying-interaction gating to `ItemEvents.USE_ON`, which wraps `Item.useOn(UseOnContext)` — the call vanilla itself only reaches *after* the block's own reaction has already declined. See the revised "Implementation surfaces" bullet above.
- Chest/door items appeared to be consumed even when placement was denied outside the claim. Guessed at the time to be the same `UseBlockCallback`-vs-`ItemEvents.USE_ON` issue; **that guess was wrong** — it survived the `ItemEvents.USE_ON` fix and was root-caused properly on the second pass below.
- No sound was audible on any denial (protection *or* pre-existing Phase 4 claim/unclaim feedback, e.g. Scepter use) during this pass. Concluded at the time to be a client/environment audio issue rather than a code defect, on the reasoning that Phase 4's identical `player.playSound(...)` calls predate this phase and no exception was thrown. **That conclusion was wrong on both counts:** it was a real defect, and "it predates this phase" was evidence *for* a shared bug rather than against one. Root-caused on the second pass below.

**Manual playtest findings (second `runClient` pass) and fixes — both remaining first-pass items closed:**

- **Denied placement consumed the item client-side.** Confirmed still broken after the `ItemEvents.USE_ON` switch, so the first pass's guess was wrong. Real cause: the client optimistically runs the very same item logic it just asked the server to run. `MultiPlayerGameMode.performUseItemOn` calls `ItemStack.useOn(...)` on the *real* held stack, restoring the count only when `hasInfiniteMaterials()` (creative) — and `useItem` likewise calls `ItemStack.use(...)` then `setItemInHand(...)` with the transformed stack, so a denied bucket showed as emptied too. The mispredicted *block* is rolled back by the prediction-sequence ack (`ClientboundBlockChangedAckPacket`), but the inventory is not: our denial means the server's stack never changed, so `AbstractContainerMenu.broadcastChanges()` diffs clean against `remoteSlots` and never sends a correction. Nothing server-side was consuming anything — the client was simply never told it had guessed wrong. Fixed with `ProtectionFeedback.resyncInventory` (`containerMenu.sendAllDataToRemote()`), called from both use hooks on denial. Deliberately **not** throttled the way `deny()` is (the throttle exists only to stop action-bar/sound spam; suppressing a resync would leave a genuine desync behind on every suppressed click), and deliberately **not** wired into break denial, which fires every tick while left-click is held and mispredicts nothing but block state.
- **No denial sound, in this phase or Phase 4.** A real defect, and one bug explaining both: `player.playSound(sound, volume, pitch)` on the server plays the sound to everyone *except* that player. `Player.playSound` delegates to `Level.playSound(entity = this, ...)`; `ServerLevel.playSeededSound` converts that entity argument into the *exclusion* argument of `PlayerList.broadcast`, whose loop skips the player it matches. In single-player there is nobody else in range, so it plays for no one. The action bar was unaffected because `sendSystemMessage` has no such inversion. Vanilla's own answer to this used to be `ServerPlayer.playNotifySound`, which no longer exists in `26.2` — likely how the code drifted onto `playSound` in the first place. Fixed with `util/PlayerSounds.playTo(player, sound)`, sending `ClientboundSoundPacket` straight to the player's connection (what `playNotifySound` did), which also keeps the cue private to the acting player, matching the action-bar message it accompanies. Applied to the protection denial *and* both Phase 4 `ScepterItem` sites — see [Phase 4](phase-4-claiming-and-unclaiming.md).

Both fixes are manual-test-only findings by nature: gametests run headless and server-side, so they can observe neither a client's mispredicted inventory nor whether a sound packet reached a client. All 32 gametests passed throughout while both bugs were live. Adding a harness for either was considered and rejected for 1.0 — the cost is a client-side test rig, and the failure mode is exactly what a manual pass is for.

## Risks & flags

Flags that stay open here and land in the [Phase 10 exploit register](phase-10-exploit-hardening-and-balance.md):

- **Exploit (accepted, monitored): TNT/creeper mining the wild.** By decision, not oversight — explosions are left as vanilla behavior for 1.0 (see the design decision above). Registered as exploit-register item #3 in Phase 10 with disposition "allow (documented)"; revisit if the balance playthrough shows it's exploited more heavily than the setup/skill cost suggests it should be.
- **Exploit (open): machines reaching across the border.** Pistons/slime contraptions inside a claim pushing, pulling, or breaking blocks in the wild; dispensers placing/breaking at the border. Not addressed in MVP — single-player self-cheating — but registered for Phase 10 (likely a config-gated border check on piston/dispenser action).
- **Exploit (open): indirect world edits.** Water/lava poured in-claim flowing into the wild (can break blocks, make obsidian), falling sand/gravel crossing the border, fire spreading from an in-claim ignition, tree growth / bone-mealed growth spilling across the border. All registered for Phase 10 dispositions.
- **Soft-lock risk (dispositioned, implementation pending in Phase 10): progression-critical world edits in the wild.** Our exposure is far smaller than the [market research](../research/market_research.md) assumes, because it calibrates to Chunklock-style *per-chunk unlock costs* — we have none, and this phase deliberately allows looting and pure interaction everywhere, so no structure is ever unreachable. The one live case: placing an eye of ender into an end-portal frame is a wild world edit that succeeds today only because the modifying-item deny-list is class-based and `EnderEyeItem` isn't on it. **Decision: close the accident rather than bless it** — `EnderEyeItem` joins the deny-list, so the rule stays uniform and the End costs a claim or three (tunnel down, portal room) exactly as nether portals already do. Registered as row #15 in the [Phase 10 exploit register](phase-10-exploit-hardening-and-balance.md) with a gametest and an End-clearing leg on the balance playthrough to prove reachability in practice.
- **Coverage gap (open): the modifying-item deny-list is class-based and blind to modded items.** Anything a mod adds that alters the world through `useOn`/`use` passes straight through enforcement. Phase 7 adds `wildDenyItems` so modpack authors can close gaps we can't enumerate; the residual gap is documented in Phase 11's known-issues, which the research found modpack authors actively look for.
- **Balance risk (major, intentional): early-game wood and food.** Trees, grass, and crops in the wild are unbreakable, so a bad first-claim placement can soft-lock progression comfort. Options for Phase 10: a config allow-list of wild-breakable blocks (plants/leaves), or doubling down (guides players to claim wisely; loot/trade for food). MVP ships strict; playtesting decides.
- Entity-based "building" (item frames, armor stands, boats, minecarts, paintings, leads) is not block placement and stays unrestricted in MVP — registered for Phase 10.
- Farmland trampling and frost-walker ice are technically wild block changes — trivial, registered for Phase 10, likely "allow".
