# Phase 4 — Claiming & unclaiming

Part of the [EmpiresMC 1.0 release plan](../1.0-release.md). Previous: [Phase 3](phase-3-the-scepter.md). Next: [Phase 5 — Protection enforcement](phase-5-protection-enforcement.md).

## Goal

The full claim lifecycle is playable with the Scepter: place the starting claim, expand when allowance permits, inspect status, and unclaim behind a cooldown.

## Design decisions

- **Claims target the chunk the player is standing in**, not the chunk of the block they're looking at — unambiguous, works mid-air and underground, and Phase 6's preview outline will make the target visible. (Raycast-targeted claiming is a backlog idea if standing-chunk feels bad in playtesting.)
- **Gesture map** (all resolved on the logical server; the client only sends the vanilla use action — fabric `SEC-001`):

  | Context | Gesture | Result |
  |---|---|---|
  | Unclaimed chunk | use | Claim it (if allowance remains) |
  | Own claimed chunk | use | Status: chunk pos, used/total chunks, tier, cooldown state |
  | Own claimed chunk | sneak-use | Unclaim — two-step: first use shows a confirm prompt, second use within ~5s commits |
  | Anywhere else | sneak-use | Reserved for the Phase 8 upgrade flow |

- **Unclaim cooldown runs on world game time** (`claimedAtTick` from Phase 2), not wall-clock — wall-clock time passes while the game is closed, which would make the cooldown meaningless in single-player. Dev default: 1 in-game day (24,000 ticks) per chunk from the moment it was claimed; configurable in Phase 7.
- **Unclaim refunds the full allowance slot** for now. This is a known balance lever — see the exploit flag below and Phase 10.
- **No adjacency requirement in the MVP.** Free-floating claims keep the Nether reachable (portal → claim a Nether chunk to mine) without special-casing dimensions. `requireAdjacency` becomes a config option in Phase 7 and a Phase 10 balance question.
- **All dimensions claimable, one shared allowance.** Simple and consistent; the Nether-progression consequences are a Phase 10 balance checkpoint (netherite is a Phase 8 upgrade cost, so Nether mining must be affordable within the curve).
- The first claim is a deliberate act: on first join (Phase 3 grant moment) the player gets a short instruction message — no auto-claimed spawn chunk.

## Steps

- [x] Implement the Scepter `use` path: resolve the standing chunk server-side, dispatch to `ClaimService`, map each typed result to a distinct feedback message + sound (claim success, no allowance, already yours, owned-by-other for future MP).
  - `item/ScepterItem.kt` overrides `Item.use(Level, Player, InteractionHand): InteractionResult` (MC `26.2` reality check: this returns a plain `InteractionResult`, not the older `InteractionResultHolder<ItemStack>`). All logic is gated on `!level.isClientSide`; the client-side call returns `InteractionResult.SUCCESS` untouched (local swing feedback only), the server-side call does the real work and returns `InteractionResult.SUCCESS_SERVER` — nothing for the client to reconcile since every effect (chat message, sound) is already server-authoritative. (Server-authoritative, but for sound that was not sufficient — see the resolved `playSound` finding below; personal cues must be packeted to the player via `util/PlayerSounds`.) The standing chunk is `ClaimKey(level.dimension().identifier(), ChunkPos.containing(player.blockPosition()))`, matching the Phase 2 `AdminCommand` pattern exactly (deliberately not the cached `Entity.chunkPosition()` field, which isn't guaranteed to reflect a same-tick position change).
  - `handleUse` branches on `service.ownerOf(key)`: `null` → `handleClaimAttempt` (dispatches `ClaimResult.Success`/`NoAllowance` from `service.claim()` to distinct messages+sounds); `== player.uuid` → `sendStatus`; otherwise → the owned-by-other message (structurally unreachable in single-player today, wired for future MP per the design decision).
- [x] Implement sneak-use unclaim with the two-step confirm (pending-confirm state per player, ~100-tick expiry) and cooldown gate; denial message includes remaining cooldown in readable form (e.g. "0.4 days").
  - New pure-Kotlin `claim/ClaimGestureService.kt` (mirrors `ClaimService`'s pure-logic/MC-glue split): `confirmUnclaim`/`requestUnclaimConfirm` implement the two-step confirm, `CONFIRM_WINDOW_TICKS = 100`. Unit-tested in `ClaimGestureServiceTest` (9 tests) with no MC bootstrap needed.
  - The cooldown gate lives in `ClaimService.unclaim(player, key, tick)` itself, not just the gesture layer — a new `tick` parameter and a new `ClaimResult.OnCooldown(remainingTicks: Long)` sealed variant, so the rule holds for every caller, not only the Scepter gesture. `UNCLAIM_COOLDOWN_TICKS = TICKS_PER_DAY = 24_000L`. `ClaimService.formatCooldownDays(ticks)` (pinned to `Locale.ROOT`) is shared by both the unclaim-denial and status-gesture messages.
- [x] Debounce repeated use events (vanilla fires use on both hands / repeatedly while held): ignore duplicate gestures within a few ticks so one click is one action.
  - `ClaimGestureService.shouldDebounce(player, tick)`, `DEBOUNCE_TICKS = 5`, checked first in `ScepterItem.use()` before any dispatch.
- [x] Extend the Phase 2 `/empiresmc admin` skeleton with debug `claim` / `unclaim` subcommands (`GAMEMASTERS`) acting on the chunk under the invoking player and **bypassing the gameplay gates** (Scepter gesture, allowance, cooldown, confirm) — a raw seeding/override tool for testing later phases (e.g. bulk-claim to exercise Phase 6 visualization or Phase 10 balance), and the mechanism that makes Phase 2's persistence exit-criterion (create a claim → save → reload → observe) manually reproducible from this phase on. A force path that skips `ClaimService`'s allowance/cooldown checks must still route the mutation through `ClaimData` and call `setDirty()`, or the override is silently lost on an unclean shutdown (the Phase 2 dirty-marking flag). Optional trailing `<player>` argument to attribute the claim to another player for future multiplayer testing.
  - `ClaimService.forceClaim(player, key, tick)` (unconditional overwrite) and `forceUnclaim(key): Boolean` (bypasses the cooldown gate entirely) — both still call the shared `onMutate` hook already wired to `SavedData.setDirty()`, so the dirty-marking guarantee holds for free. `command/AdminCommand.kt`'s `claim [<player>]` / `unclaim` subcommands wrap these; the chunk is always the invoking player's standing chunk, only claim attribution moves with the optional `<player>` argument. These force methods turned out to have a second, unplanned use: they're also what the Phase 4 gametests use to seed an already-cooldown-elapsed claim, since GameTest exposes no public API to fast-forward `Level.getGameTime()` (see the gametest note below).
- [x] First-join instruction message ("Use your Scepter in a chunk to claim your first land") wired into the Phase 3 grant.
  - `item/ScepterGrant.kt`'s `grantOnFirstJoin` sends `Component.translatable("empiresmc.claim.first_join_instruction")` immediately after the item is placed in the inventory.
- [x] All feedback via translatable components in `en_us.json` (fabric `DEV-013`).
  - 12 new keys under `empiresmc.claim.*` in `assets/empiresmc/lang/en_us.json`, checked by hand against every `Component.translatable` call site added this phase (the admin debug command's own output stays plain `Component.literal`, matching its Phase 2 precedent as a dev-only tool, not player-facing feedback).
- [x] Gametests: claim happy path; allowance exhaustion at 1 chunk; status gesture; unclaim blocked before cooldown; unclaim succeeds after cooldown (fast-forward world time); confirm-expiry cancels the unclaim; refunded slot is claimable elsewhere.
  - 7 new tests in `EmpiresMCGameTest.kt`, all driving `ModRegistry.SCEPTER.use(...)` directly (same technique the Phase 3 tests use for Fabric events) rather than a simulated client packet round trip.
  - **Two GameTest environment quirks discovered and worked around (candidates for a new fabric rule):** (1) every `GameTestHelper.makeMockServerPlayerInLevel()` player is placed at literal world position `(0, 0, 0)`, not somewhere relative to its own test structure, and all tests in a batch share one `MinecraftServer`/world/`SavedData` — so tests that touch shared server state (like our `ClaimService`) must pick their own disjoint keys rather than relying on "the standing chunk" being test-local. Each test below now moves its mock player to a random, far-from-origin chunk before exercising a gesture. (2) `GameTestHelper.setTime()` only advances the per-dimension day/night clock (`ServerClockManager`), not `Level.getGameTime()` — there is no public API to fast-forward the raw world tick counter our cooldown is measured against. The "unclaim succeeds after cooldown" and "confirm-expiry" tests instead seed `ClaimRecord.claimedAtTick` in the past via `ClaimService.forceClaim`, the same seeding path the admin debug command uses.
  - Confirm-expiry (`sneakUseAfterTheConfirmWindowExpiresRePromptsInsteadOfUnclaiming`) genuinely waits out the ~100-tick window via `GameTestHelper.runAfterDelay` with `@GameTest(maxTicks = 150)` (the framework default is 20) rather than asserting on `ClaimGestureService` directly, so the real `ScepterItem.use()` wiring is what's under test, not just the pure logic (which `ClaimGestureServiceTest` already covers independently).

## Risks & flags

- **Exploit — nomadic strip-mining:** claim a chunk, exhaust its resources, wait out the cooldown, unclaim, claim virgin land, repeat. The cooldown throttles but does not close this; a full close needs a refund penalty (`unclaimRefundPercent < 100`) or per-chunk "scarring". Deliberately deferred to Phase 10 balance with config knobs from Phase 7 — do not try to solve it in this phase.
- **Exploit — time skipping (investigated and RESOLVED in the Phase 4 QA pass — no non-cheat vector affects the cooldown):** originally documented as "sleeping and `/time set` advance world time, shortening the cooldown," accepted as a conscious 1.0 trade-off. Fully bytecode-traced against the pinned MC `26.2` deobf jar this pass. The cooldown compares `Level.getGameTime()` (`ClaimService.unclaim`'s `tick`), and `ServerLevel.tickTime()` is the only writer of it — `+1` per real tick, nothing else outside NBT load. Everything that "skips time" in `26.2` goes through the *separate* `ServerClockManager`/`WorldClock` day-night system instead: sleeping calls `moveToTimeMarker(..., WAKE_UP_FROM_SLEEP)`; `/time set` calls `ServerClockManager.setTotalTicks`; `/time add` calls `addTicks` — **none of them touch `getGameTime()`.** Confirmed: **neither sleeping nor `/time set`/`/time add` has any effect on the unclaim cooldown** (the original note was wrong on both counts; the earlier sleeping-only correction is now verified and extended to `/time set`). The only ways to elapse it are letting real ticks pass (idling ~20 real minutes = one in-game day, the intended mechanic) or the operator/cheat `/tick sprint`/`/tick step` commands — which genuinely fast-run the whole world rather than bypassing the timer, so they're left as an accepted cheat-command trade-off (the same category the original note wrongly assumed `/time set` was). A normal survival player waits the real cooldown; there is no exploit to close here.
- **Gesture collision risk:** sneak-use means "unclaim" inside a claim and "upgrade" (Phase 8) outside it — a player standing one step wrong could trigger the wrong flow. Both flows therefore require a confirm step, and both print which chunk/action they're about to commit. If playtesting still shows misfires, a management GUI (backlog) replaces gestures.
- Claiming currently has no cost beyond allowance — the "cost" of expansion is entirely the Phase 8 upgrade ladder. If playtesting wants per-claim costs too (e.g. consume an item per chunk), that's a new config knob + phase, not a rework, because `ClaimService` already returns typed denials.

## QA/QC review findings (independent sign-off pass)

Independent review of the committed Phase 4 work. `./gradlew build` is green (35 unit + 16 gametests, 0 failures, re-verified this pass) and every code path was traced by hand. **No blocking bugs** — the items below are logged for one-by-one follow-up and none needs to land before Phase 5 unless we decide otherwise. Severity in brackets.

- [x] **[resolved — doc only] Time-skip exploit reconciled.** Bytecode-confirmed that sleeping and `/time set`/`/time add` have zero effect on the cooldown; only real elapsed ticks (intended) or `/tick sprint`/`step` (cheat) advance it. No code change — the Risks & flags bullet above was rewritten to close the open question.
- [x] **[resolved] Stale cross-world gesture state (single-player).** `ClaimGestureService.clear()` wipes both the debounce and pending-unclaim maps; `ScepterItem`'s `init` block registers it against `ServerLifecycleEvents.SERVER_STARTED` (same event `ClaimDataAccess` already attaches to), so every fresh or reloaded world starts with no leftover gesture state from the last one. Covered by two new `ClaimGestureServiceTest` cases (11 total in the file now).
- [x] **[resolved] "0.0 days" feedback in the final minute of cooldown.** Reworked in three parts: (1) the unit changed from in-game days to real minutes (`ClaimService.formatCooldownMinutes`), since "days" implied the daylight-cycle clock even though the cooldown deliberately ignores sleep/`/time set` (see the Risks & flags bytecode note above); (2) the format dropped the decimal for a plain whole-minute count, rounded up (never down) so it never understates the wait — covered by `formatCooldownMinutesFormatsWholeMinutesRoundedUp` in `ClaimServiceTest`; (3) under a minute remaining, `ScepterItem`'s new `cooldownComponent` helper switches both the status readout and the unclaim denial to a dedicated "less than a minute" message (`empiresmc.claim.status.cooldown_remaining_soon` / `empiresmc.claim.unclaim_cooldown_soon`) instead of rounding a few seconds up to "1 more minute".
- [x] **[resolved] Sneak-to-claim confusion.** `handleSneakUse` now branches on `owner == null` vs. owned-by-other before picking the reserved-for-upgrade message: the unclaimed case gets a new `empiresmc.claim.upgrade_reserved_unclaimed` key ("...Stop sneaking and use again to claim this chunk."), the owned-by-other case keeps the plain original wording (releasing sneak there still wouldn't claim it, so the hint would be misleading). Contextual fix at the moment of confusion rather than bloating `first_join_instruction` up front.
- [x] **[resolved — doc only] Status gesture suppressed when looking at an interactable block — confirmed vanilla behavior, not a bug.** Bytecode-traced `ServerGamePacketListenerImpl.handleUseItemOn`/`ServerPlayerGameMode.useItemOn` against the pinned `26.2` deobf jar: aiming at a block within reach sends `ServerboundUseItemOnPacket`, whose handler never falls back to `useItem`/`Item.use()` — that path only runs from the separate `ServerboundUseItemPacket` sent when nothing block-shaped is in the crosshair. For a chest/furnace/door, `BlockState.useWithoutItem` (the block's own right-click GUI) consumes the interaction before `Item.useOn`/`Item.use` are ever reached, so no `ScepterItem` override could intercept it short of a mixin into the block's own interaction path — which would also break opening containers/doors while holding the Scepter, a worse trade for a cosmetic status readout. Also verified the finding's other half by tracing the same bytecode: `useItemOn` skips the block-interaction branch entirely whenever `isSecondaryUseActive() && (either hand non-empty)`, true any time the player sneaks with the Scepter in hand — so sneak-use (unclaim/confirm) genuinely reaches `Item.use()` regardless of crosshair target, confirming claiming/unclaiming are unaffected. No code change; players who want status while aimed at furniture just glance away first.
- [x] **[resolved] Held right-click auto-repeats gestures (~every 8 ticks).** Split the finding's two halves: the confirm-undercutting half was the real risk, so `ClaimGestureService.confirmUnclaim` now enforces a `MIN_CONFIRM_TICKS` (20-tick) floor between a sneak-use request and its confirm — well above vanilla's ~4-tick held-use repeat cadence but far under the 100-tick confirm window, so a genuine release-and-reclick is unaffected. Because a rejected-too-soon attempt clears the pending entry and `ScepterItem.handleSneakUse`'s existing re-request-on-false path immediately restarts the clock, a continuously held button can never confirm — only a deliberate second press after the floor can. Covered by two new `ClaimGestureServiceTest` cases and a new gametest (`heldSneakUseRepeatsDoNotConfirmUntilTheMinimumConfirmWindowPasses`); the existing `sneakUseTwiceUnclaimsAfterTheCooldownHasElapsed...` gametest's inter-click delay moved from `DEBOUNCE_TICKS+1` to `MIN_CONFIRM_TICKS+1` to reflect the now-deliberate confirm. The status-readout message/sound spam while holding on your own chunk is left as accepted low-severity cosmetic behavior — it's not exploitable, just noisy, and gating it would need the same debounce tightening that (as analyzed) can only delay, not close, the confirm exploit, so it wasn't worth doing for its own sake.
- [x] **[resolved during Phase 5 — latent since this phase shipped] Scepter feedback sounds never actually played.** Every sound this phase wired up (claim success, denial, unclaim confirm/success, status readout) was silently inaudible from the day it landed, and the gametests could not see it: they assert claim state, not that a sound packet reached a client, and the exit-criteria manual pass above was deferred, so nothing exercised it until Phase 5's playtest. Cause: `player.playSound(sound, volume, pitch)` on the server plays to everyone *except* that player — `Player.playSound` delegates to `Level.playSound(entity = this, ...)`, and `ServerLevel.playSeededSound` turns that entity into the *exclusion* argument of `PlayerList.broadcast`. In single-player, nobody hears it. (Vanilla's `ServerPlayer.playNotifySound`, the method meant for this, was removed in `26.2`.) Fixed by routing both `ScepterItem` call sites through the new `util/PlayerSounds.playTo`, which sends `ClientboundSoundPacket` to the player's own connection. Full root-cause in the [Phase 5 doc](phase-5-protection-enforcement.md); confirmed audible by manual playtest.
- [x] **[resolved] Duplicated cooldown-remaining math.** Extracted `ClaimService.remainingCooldownTicks(record, tick)`; both `unclaim` and `ScepterItem.sendStatus` now call the single helper instead of each computing `UNCLAIM_COOLDOWN_TICKS - (tick - claimedAtTick)` independently.
- [x] **[resolved — coverage] No gametest for the `upgrade_reserved` branch.** Added `sneakUseOnAnUnclaimedChunkDoesNotClaimIt` in `EmpiresMCGameTest.kt`: sneak-use on a chunk nobody owns must land in `handleSneakUse`'s `owner == null` branch (the `upgrade_reserved_unclaimed` message) rather than the claim path plain `use()` exercises, and must leave the chunk unclaimed. 18 gametests green (was 17). (`owned_by_other` remains genuinely unreachable in single-player — left uncovered.)
- [x] **[resolved] Pluralization polish.** The original "in 1.0 days" awkwardness was superseded by the minutes rework above, but that rework introduced the same issue at a new boundary: whole-minute counts made "1 more minutes" reachable at exactly one minute remaining. Fixed with the per-count message variants this note originally suggested — `ScepterItem`'s `cooldownComponent` helper now takes a singular key alongside the plural one and switches to it when `formatCooldownMinutes` returns `"1"` (`empiresmc.claim.status.cooldown_remaining_one` / `empiresmc.claim.unclaim_cooldown_one`, both fixed "1 more minute" strings with no placeholder).
