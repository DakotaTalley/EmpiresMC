# Phase 3 — The Scepter

Part of the [EmpiresMC 1.0 release plan](../1.0-release.md). Previous: [Phase 2](phase-2-claim-data-and-persistence.md). Next: [Phase 4 — Claiming & unclaiming](phase-4-claiming-and-unclaiming.md).

## Goal

The Scepter exists as a registered item the player receives on first join and can never permanently lose — without any gameplay-inhibiting restrictions like "cannot drop".

> **Revised during implementation (review findings).** The original loss-protection design leaned on two mixins — keep-on-death via an `Inventory.dropAll()` injection, plus dropped-item hardening. A review of the built code found the keep-on-death mixin was **broken**: it preserved the Scepter on the *dying* entity, but vanilla builds a fresh inventory on respawn and only copies the old one when `keepInventory` is on, so a normal death silently lost the item — and worse, it suppressed the otherwise-recoverable ground drop. The explosion-immunity claim was also wrong under default gamerules. The approach was reworked to be **mixin-free**: keep-on-death is now a re-grant on `ServerPlayerEvents.AFTER_RESPAWN`, fire/lava immunity stays (it genuinely works), and the fussier passive protections (never-despawn on the ground, explosion immunity) were dropped in favour of the recovery recipe. Losing the Scepter to an explosion, the void, or an abandoned drop is an accepted, re-craftable outcome; the finer balance is deferred to release-time polish. The steps and exit criteria below have been updated to what actually shipped.

## Design decisions

- **The Scepter is a stateless handle.** No tier, no claim data, no owner stored on the `ItemStack` — all of that lives in the Phase 2 server-side profile keyed by the *holder's* UUID. This one decision is the whole loss-protection strategy:
  - Losing the item never loses progress; any replacement Scepter reflects the same empire.
  - Duplication (creative middle-click, inventory tricks) is harmless — two Scepters are two handles to the same state.
  - Recovery can be a cheap crafting recipe with no "is this the real one" logic.
  - In any future multiplayer mode, whoever holds *a* scepter acts on *their own* empire — no theft or transfer semantics needed.
- **Layered protection, no gameplay friction** (the item stays droppable, storable, hopper-able). Revised to a mixin-free shape (see the note above):
  1. Keep on death — on respawn the Scepter is re-granted to any entitled player who came back without one. This covers the `keepInventory`-off death (the only case where vanilla drops it) and is a no-op when the inventory was already carried across. A brief, harmless duplicate can exist — the dropped copy despawns while the player already holds a fresh one — which is fine by the stateless-handle design.
  2. Fire/lava immunity — netherite-style `fireResistant()` settings, which cover the item and any dropped item entity. **Kept** because it is free and genuinely works.
  3. Recovery — a cheap, always-available crafting recipe (dev placeholder: stick + iron ingot, shapeless) plus `/empiresmc admin scepter`. This is now the sanctioned path for the losses the passive layer no longer prevents (explosion, void, an abandoned drop that despawns).
- **Dropped from the original plan:** never-despawn on the ground (redundant once respawn re-grants, and it would litter the world one Scepter per death) and explosion immunity (never worked under default gamerules). Both are "losing the Scepter" edge cases now handled by recovery; whether to tighten either is tracked for the [Phase 10](phase-10-exploit-hardening-and-balance.md) balance pass (exploit register #14), so the decision isn't lost.
- **Dev-placeholder visuals per the project brief:** stick model/icon, item named "Scepter", rarity Epic so the name reads as special. Real art lands in Phase 9.
- Item settings: `maxCount = 1` (no stacking; keeps the tooltip/HUD semantics simple).

## Steps

- [x] Register `ScepterItem` in the Phase 1 registry holder: fireproof-style settings, max count 1, Epic rarity; stick model + `item.empiresmc.scepter` translation key (fabric `DEV-013`: a missing lang entry shows the raw key — add `en_us.json` now).
  - MC `26.2` reality check (verified against the actual merged jar, not assumed): item registration is `Registry.register(BuiltInRegistries.ITEM, id, Item(properties))` with `Item.Properties` (not `Settings`) — `registry/ModRegistry.kt`. `Item.Properties().setId(...).stacksTo(1).rarity(Rarity.EPIC).fireResistant()`. Item models are now a two-file indirection: `assets/empiresmc/items/scepter.json` (`{"model": {"type": "minecraft:model", "model": "empiresmc:item/scepter"}}`) pointing at the classic `assets/empiresmc/models/item/scepter.json` (parent `minecraft:item/handheld`, `layer0` = `minecraft:item/stick` — reuses the vanilla stick texture, no new asset). `item/ScepterItem.kt` extends `Item`, overriding `appendHoverText` for the tooltip step below.
  - `assets/empiresmc/lang/en_us.json` carries `item.empiresmc.scepter` plus the two tooltip keys from the tooltip step.
- [x] First-join grant: on player join, if the profile's `receivedScepter` flag is unset, give one Scepter and set the flag (flag prevents re-grant spam; recovery goes through the recipe instead).
  - `ClaimService.grantScepterIfNeeded(player): Boolean` is the sole write path (flips the flag exactly once, calls `onMutate()`, returns whether it actually granted — unit-tested both for the flag flipping and for preserving other profile fields on `copy()`). `item/ScepterGrant.kt` registers on Fabric API's `ServerPlayerEvents.JOIN` and gives an `ItemStack(ModRegistry.SCEPTER)` via `player.inventory.add(...)` when the service says to.
- [x] Keep-on-death: retain the Scepter through respawn. **Reworked from the original mixin plan** — the first implementation injected `Inventory.dropAll()` to stash/restore the Scepter, but review showed that only preserves it on the *dying* entity: `PlayerList.respawn` builds a fresh `ServerPlayer`/`Inventory`, and `ServerPlayer.restoreFrom` copies the old inventory only when `keepInventory` is on, so a normal death lost it anyway (and suppressed the otherwise-recoverable ground drop). Reworked to a re-grant on `ServerPlayerEvents.AFTER_RESPAWN`; no mixin of our own.
  - `item/ScepterGrant.kt` registers `AFTER_RESPAWN` and re-grants an `ItemStack(ModRegistry.SCEPTER)` when the respawned player is entitled (`profileOf(uuid).receivedScepter`) **and** is not already holding one. That "already holding one" guard is what makes it correct across every respawn path: it fires only on a `keepInventory`-off death (where vanilla didn't copy the inventory) and no-ops when `keepInventory` is on or when returning from the End (vanilla already carried the Scepter). Confirmed against the pinned Fabric API jar that `PlayerListMixin` fires `AFTER_RESPAWN` at the tail of `PlayerList.respawn`.
- [x] Dropped-entity hardening — **scope reduced from the original plan.** Only fire/lava immunity shipped; never-despawn and explosion immunity were dropped (see the note at the top).
  - **Fire/lava immunity (kept, no mixin):** confirmed from the `ItemEntity` bytecode that `ItemEntity.fireImmune()` defers to `ItemStack.canBeHurtBy`, which checks the `DAMAGE_RESISTANT` component that `Item.Properties.fireResistant()` already populates. Covers the item and any dropped Scepter entity for free.
  - **Never-despawn (dropped):** the original `mixin/ItemEntityMixin.kt` calling `setUnlimitedLifetime()` was removed. Once respawn re-grants the Scepter it is redundant for the death case, and keeping it would litter the world with one un-despawning Scepter per death (the dropped copy the re-grant intentionally leaves behind). An abandoned manual drop now despawns like ordinary loot; recovery re-obtains it.
  - **Explosion immunity (dropped):** the original plan claimed this was free via `ItemEntity.ignoreExplosion()`, but the bytecode shows the opposite under default gamerules — a standard TNT blast (`DESTROY_WITH_DECAY`, `mobGriefing` on) *does* affect the item, and `fireResistant()`'s `DAMAGE_RESISTANT` component does not cover explosion damage, so the dropped Scepter is destroyed. Deferred to release-time polish/balance; recovery covers it meanwhile.
- [x] Recovery recipe (data-generated or JSON under `data/empiresmc/recipe/`): cheap, unconditional. Harmless to craft twice by design.
  - Plain JSON (`data/empiresmc/recipe/scepter.json`), not data-generated — no datagen entrypoint exists yet in this project and adding one for a single recipe was out of scope. MC `26.2`'s ingredient shape changed from the old `{"item": "..."}` object form to bare strings (verified against real vanilla recipes in the jar): `"ingredients": ["minecraft:stick", "minecraft:iron_ingot"]`, `"type": "minecraft:crafting_shapeless"`. `AdminCommand`'s new `scepter` subcommand (`/empiresmc admin scepter`) is the second recovery path called for in the design decisions, giving the invoking player a Scepter unconditionally.
- [x] Static tooltip: flavor line + "used / total chunks shown while claim data is synced" placeholder (live numbers arrive with Phase 6 client sync).
  - `ScepterItem.appendHoverText` appends `item.empiresmc.scepter.tooltip.flavor` and `item.empiresmc.scepter.tooltip.chunks_placeholder` after the vanilla text. Mojang marks this override point `@Deprecated` in the jar (a "don't call this directly, override only" marker, not a sign a replacement exists — confirmed no alternate overload exists) — suppressed with `@Suppress("OVERRIDE_DEPRECATION", "DEPRECATION")`, not worked around.
- [x] Tests: unit test the grant-flag logic; gametest the join grant, the respawn restore, and recovery.
  - `ClaimServiceTest`: 2 tests (`grantScepterIfNeededGrantsExactlyOnce`, `grantScepterIfNeededPreservesExistingProfileFields`) — pure logic, no MC bootstrap needed.
  - `EmpiresMCGameTest`: `freshPlayerReceivesExactlyOneScepterOnJoin`, `rejoinGrantsNoAdditionalScepter` (invoke `ServerPlayerEvents.JOIN` directly); `respawnRestoresScepterWhenPlayerCameBackWithoutOne` and `respawnDoesNotDuplicateScepterThatSurvived` (drive the `AFTER_RESPAWN` listener directly — the restore, and the no-duplicate guard); `realDeathRespawnRestoresExactlyOneScepter` (end-to-end: a genuine `die()` + `PlayerList.respawn` under `keepInventory` off, asserting the *returned* new player holds exactly one — the test the original mixin approach would have failed); `recoveryRecipeIsLoaded`. `adminCommandsExecuteSuccessfully` also drives `empiresmc admin scepter`.
  - **Environment quirk recorded as fabric `DEV-015`:** a mock/embedded gametest player's connection never reports `hasClientLoaded()`, making `ServerPlayer.isInvulnerableTo()` unconditionally `true`, so `hurtServer(...)` silently no-ops. The end-to-end test kills with `player.die(damageSource)` instead, which skips that gate and drives the real death path.

## Risks & flags

- **Do not add per-stack NBT "convenience" state later** (e.g. caching tier on the stack for tooltips) without treating it as pure display cache — the moment stack NBT becomes authoritative, every dupe/loss protection above collapses. Phase 6's sync layer is the sanctioned way to get live client-side numbers.
- Keep-on-death interacts with other mods' grave/corpse mods — out of scope for 1.0, note in README known-issues at release.
- The recovery recipe means the Scepter is craftable before first join edge-cases (multiplayer/LAN) — harmless by design, but worth a test once multiplayer is ever targeted.
- `keepInventory` gamerule already covers death; the keep-on-death path must not duplicate the item when both are active.
  - **Handled by the "already holding one" guard:** with `keepInventory` on, vanilla carries the Scepter across, so the `AFTER_RESPAWN` re-grant sees the player already holding one and no-ops. `respawnDoesNotDuplicateScepterThatSurvived` covers exactly this.

## Exit criteria

- [x] Fresh world: player spawns holding nothing, receives the Scepter on join, message/tooltip render with no raw translation keys.
  - Verified structurally: every `Component.translatable` key used (`item.empiresmc.scepter` and the two tooltip keys) has a matching `en_us.json` entry (fabric `DEV-013` — a mismatch here doesn't error, it just shows the raw key, so this was checked by hand against the lang file, not inferred). Grant-on-join and exactly-once behavior covered by `freshPlayerReceivesExactlyOneScepterOnJoin`/`rejoinGrantsNoAdditionalScepter`.
- [x] Scepter is never permanently lost across player death (with and without `keepInventory`) and being dropped into lava. **Revised:** the original criterion also listed surviving a TNT blast and a 6000+ tick ground wait as *passive* guarantees — those were dropped (see the top note) and are now covered by re-obtaining the Scepter, not by the item itself surviving.
  - Death (both `keepInventory` states): gametested end-to-end — `realDeathRespawnRestoresExactlyOneScepter` for the drop-and-respawn case, `respawnDoesNotDuplicateScepterThatSurvived` for `keepInventory` on.
  - Lava/fire: `fireResistant()`'s `DAMAGE_RESISTANT` component, verified from the `ItemEntity`/`ItemStack` bytecode as a vanilla mechanism triggered by item registration. A live lava gametest is cheap to add later if it regresses.
  - TNT blast and 6000+ tick ground wait: **no longer passive guarantees.** A dropped Scepter is destroyed by a default-gamerules explosion, and an abandoned one despawns normally; both are re-craftable via the recovery recipe. Tightening either is release-time polish/balance.
- [x] Losing it into the void, then crafting the recovery recipe, yields a working Scepter.
  - Void loss needs no special handling by design (the Scepter is a stateless handle — see design decisions). `recoveryRecipeIsLoaded` confirms the recipe is actually registered (a malformed shape fails to load silently otherwise); the crafted result is `empiresmc:scepter`, the same registry entry the join-grant and admin-command paths use, so "a working Scepter" follows from it being the identical item, not a special case.
